RabbitMQ 概述

Created2026-06-17|Updated2026-06-25|RabbitMQ
|Post Views:

RabbitMQ 使用 Erlang 语言开发的开源消息队列系统，基于 AMQP 协议实现。

概述

优势

  • 开源、性能优秀，稳定性保障
  • 提供可靠消息投递模式(confirm)、返回模式(return)
  • 与 Spring AMQP 成熟集成
  • 集群模式丰富
  • 保证消息不丢失的前提做到高可靠性、可用性

AMQP 高级消息队列协议

AMQP(Advanced Message Queuing Protocol 高级消息队列协议) 是具有现代特征的二进制
协议。提供统一消息服务的应用层标准高级消息队列协议。为面向消息中间件设计的应用程开发标准协议。

AMQP 核心概念

  • Server: 又称 Broker 接受客户端连接，实现 AMQP 实体服务（每个 RabbitMQ 服务器都是一个 Broker ）

  • Connection: 连接，应用程序与 Broker 的网络连接

  • Channel: 网络信道，代表一个消息会话，对消息的读写都是在 Channel 中进行，一个客户端可以有多个 Channel

  • Message: 消息，服务器与应用程序之间传递的数据，由 Properties 和 Body 构成

    • Properties 消息属性（优先级、延迟等高级特性）
    • Body 消息体内容

  • Virtual host: 虚拟主机，用于逻辑隔离最上层的消息
    一个 Virtual Host 可以有若干个 Exchange 和 Queue 并且不能重复；不同的 Virtual Host 可以用来隔离不同的微服务域。

  • Exchange: 交换机，接收消息并根据路由键转发消息到绑定的队列

  • Binding: Exchange(交换机)和Queue(队列)之间的虚拟连接， Binding 中可以包含 routing key

  • Routing key: 用来确定交换机到队列之间的路由规则

  • Queue: 也成为 Message Queue(消息队列)，实际保存消息并将消息转发给消费者

RabbitMQ 核心概念

  1. ConnectionFactory 获取连接工厂(配置Broker IP/Port username/password)
  2. Connection: 通过工厂获取链接
  3. Channel: 通过连接创建数据信道，发送和接收消息
  4. Queue: 具体的消息存储队列
  5. Producer & Consumer: 生产和消费者

消费者支持两种消费模型：push 推送 和 pull拉取 两种方式

交换机(Exchange)

交换机(Exchange): 接受消息，根据路由键转发消息到所绑定的队列。

交换机配置属性

  • Name: 交换机名称
  • Type: 交换机类型
    • direct 直连交换机
    • topic: 主题交换机
    • fanout: 扇出交换机
    • headers: 头交换机
    • sharding(通过插件 rabbitmq_sharding支持):
  • Durability: 是否持久化(true: 持久化)
  • Auto Delete: 自动删除；当最后一个绑定到交换机上的队列删除后，是否自动删除交换机
  • Internal: 当前交换机是否用于 RabbitMQ 内部使用，默认 false
  • Arguments: 扩展参数，用于扩展 AMQP 协议自定义使用

交换机类型

  • direct: 直连交换机(默认名称： #empty string# / amqp.direct)

    所有发送到直连交换机的消息被转发到与 routing key 绑定的队列。如果绑定队列不存在，则丢弃消息。

    通过 channel.queueBind() 将 routing key 与队列绑定。

    直连主交换机模式可以使用 RabbitMQ 自带的交换机: default exchange ，所以不需要将交换机(exchange)进行任何绑定(
    binding)操作；

    消息传递时， routing key 必须完全匹配才会被队列接收，否则将被丢弃(即，使用默认交换机时的 routing key 与队列名
    必须是相同的)。

  • topic: 主题交换机(默认名称： amqp.topic)

    所有发送到主题交换机的消息通过通配符匹配进行路由，将消息发送到匹配的队列。

    routing key 与 bingding key 可以模糊匹配时，消息被传递到绑定 binding key 的队列中。

    Topic 交换机 Routing key 通配符：

    • . 分隔不同的词
    • # 匹配一个或多个词
    • * 匹配一个词

  • fanout: 扇出交换机(默认名称： amqp.fanout)

    (不使用 routing key)简单的将队列绑定到交换机。发送到交换机的消息都会被转发到与该交换机绑定的所有队列上。

    扇出交换机转发消息是最快的（不需要做匹配）。

  • headers: 头交换机；根据头部信息进行路由(默认名称：amqp.match/amqp.heardes)

  • sharding: 通过插件 rabbitmq_sharding支持

队列(Queue)

Queue 实际存储消息数据。

队列配置属性

  • Name: 队列的名称
  • Durability: 是否持久化，(Durable 是，Transient 否)
  • Exclusive: 独占，只被一个连接(connection)使用，当连接关闭后队列被删除
  • Auto delete: 是否自定删除；当设置自动删除时，最后一个监听被移除后队列会自动被删除
  • Arguments: 额外的高级控制参数

连接(Connection)

连接通常是长连接，使用认证机制并且提供 TLS (SSL) 保护。

通道(Channel)

通道处理多个连接，实现对连接复用（即，多个通道共享同一个连接）。

绑定(Binding)

Binding 绑定描述交换机与交换机或队列之间的连接关系。

Binding 中可以包含 routing key 或者其它参数。

消息(Message)

服务器与应用程序之间传递的数据。

消息由 Properties 和 Payload(Body) 组成。

消息属性

  • delivery mode: 持久化方式
  • headers: 自定义内容
  • content_type: 编码字符集
  • content_encoding
  • priority: 优先级
  • correlation_id: 消息唯一 id
  • reply_to: 重试队列
  • expiration: 过期时间
  • message_id: 消息id

常用的自定义属性：

  • timestamp: 时间戳
  • type:
  • user_id:
  • app_id:
  • cluster_id:

虚拟主机(Virtual host)

虚拟主机用于进行逻辑隔离，最上层的消息路由。一个虚拟主机中可以有多个交换机和队列。

同一个虚拟主机中不能有同名的交换机与队列。

RabbitMQ 高级特性

生产端消息可靠投递

关注点：

  • 保障消息的成功发出
  • 保障 MQ 节点的成功接收
  • 发送端收到 MQ 节点(Broker)确认应答
  • 完善的消息进行补偿机制

解决方案

消息要首先写入数据库后在进行发送，而不是先发送后入库。

方案一：消息信息落库，对消息状态进行打标

  1. 业务数据与消息信息落库(两次数据库操作)
  2. 消息发送
  3. 生产端的 Confirm Listener 监听接收消息应答 confirm
  4. 更新消息信息库记录为已可靠投递
  5. 分布式定时任务查询消息信息未成功投递的记录
  6. 重试消息发送
  7. 当消息超过重试次数，更新消息为投递失败，由补偿机制处理

缺点：需要读取两次数据库写入操作，在高并发下将造成数据库瓶颈。

方案二：消息延迟投递，做二次确认，回调检查

  1. 业务数据落库
  2. 发送消息
  3. 延迟消息投递检查
  4. 消费者消费消息
  5. 发送 confirm 确认消费
  6. 在 Callback service 中接收到监听的确认消费消息
  7. 检查消息细节，在 Step2 延时到达时确定是否有匹配的 Confirm ，如果没有则通过 RPC 调用 Upstream service 消息重发。

减少写入数据库，保证吞吐。

消费端消息幂等性保障

幂等性概念

对一个操作重复执行时结果不会产生差异。

消费端实现幂等性，即消息永远不会消费多次。

解决方案

方案一：唯一 ID + 指纹码 机制(利用数据库主键去重)

  1. 唯一 ID + 指纹码 机制，利用数据库主键去重
  2. SELECT COUNT(1) FROM T_ORDER WHERE ID = 唯一 ID + 指纹码
  • 优势： 实现简单
  • 缺点： 高并发下有数据库写入的性能瓶颈

优化方案： 根据 ID 进行分库分表进行算法路由

方案二：Redis 分布式锁

需要考虑的问题：是否要进行数据库落库

  • 如果落库，关键解决的问题是数据库和缓存如何做到原子性
  • 如果不需要落库，数据存储到缓存中，如何设置定时同步的策略

Confirm 确认消息

  • 消息的确认是指生产者投递消息后，如果 Broker 收到消息，则会给生产者一个应答；
  • 生产者接收应答来确认消息是否正常发送到了 Broker

这种消息确认机制是消息的可靠性投递的核心保障。

解决方案

使用 Confirm 确认消息

. 在 channel 上开启确认模式: channel.confirmSelect()
. 在 channel 上添加监听: addConfirmListener ，监听成功和失败的返回结果，根据具体的结果对消息进行重新发送或记录日志等后续处理

Return 消息机制

Return Listener 用于处理不可路由的消息，用于生产端。

如果发送消息的时候，当前的 exchange 不存在或者指定的 routing key 路由不到时，需要使用 Return Listener 监听这种不可达的消息。

解决方案

使用 Return 消息机制

  • Mandatory:
    • true —— 则监听接收到路由不可达的消息，然后进一步处理
    • false —— Broker 端自动删除该消息

消费端自定义监听

消费者可以通过自定义监听来实现对消息的处理逻辑。
自定义类继承 DefaultConsumer 实现 handleDelivery 方法实现。

消费端限流

削峰：

假如 RabbitMQ 服务器有上万条未处理的消息，当一个消费端连接时将收到大量消息，导致客户端无法同时处理消息，甚至导致消费端服务崩溃。

RabbitMQ 提供 QoS(服务质量保证) 功能，即在非自动确认消息的前提下，如果一定数目的消息未被确认前，不进行消费新的消息。

QoS 通过基于 Consume 或者 Channel 设置

接口方法: void basicQos(int prefetchSize, int prefetchCount, boolean global)

  • prefetchSize 消息大小,0: 不限制

  • prefetchCount 每次处理的最大消息数量，直到 ack 消费确认后，再推送新消息

    perfetchCount 在 no_ack=false 的情况下生效。

  • global 作用级别

    • true 当前连接下的所有 Channel 都生效
    • false 仅对当前 Channel 生效

消费端 ACK 与重回队列

消息确认类型：

  • ACK: 处理成功
  • NACK: 处理失败，Broker 重新发送消息

消费端的重回队列:

消费端重回队列是为了对没有处理成功的消息，把消息重新回递给 Broker。返回给 Broker 的消息将会被放到队列的最尾端。

一般在实际应用中，都会关闭重回队列。

TTL

TTL 是 Time To Live 的缩写，即生存时间。

RabbitMQ 支持的 TTL 类型:

  • RabbitMQ 支持消息的过期时间，在消息发送时可以指定。
  • RabbitMQ 支持队列的过期时间，从消息入队列开始计算，只要超过了队列的超时时间配置，消息会自动清除。

死信队列

死信队列: DLX(Dead-Letter-Exchange)用于处理无法被消费的消息。

当消息无法被消费或处理，并且达到一定的条件时，消息会被重新路由到死信队列中。死信队列能够帮助系统对无法正常处理的消息进行处理，以便进行分析、监控或者重新处理。DLX
也是一个正常的 Exchange 和一般的 Exchange 没有区别，它能在任何队列上被指定，实际上就是设置某个队列的属性。

当队列中有死信时， RabbitMQ 会自动将这个消息重新发布到设置的 Exchange 上去，进而被路由到另一个队列。

消息进入死信队列的条件

  • 消息被拒绝(basic.reject/basic.nack) 并且 requeue=false
  • 消息 TTL 过期
  • 队列达到最大长度

使用死信队列

  1. 首先设置死信队列的 Exchange 和 Queue 然后继续宁绑定:

    • Exchange: dlx.exchange
    • Queue: dlx.queue
    • RoutingKey: #

  2. 在正常声明交换机、队列、绑定时在队列上加上参数:

    arguments.put("x-dead-letter-exchange", "dlx.change");

  3. 消息在过期、requeue、队列在达到最大长度时，消息就可以直接路由到死信队列

延迟机制

延迟机制使用延迟插件实现。

延迟机制可以用于：消息的延迟推送、定时任务（消息）的执行、与消息重试策略配合、业务削峰限流、降级的异步延迟消费等。

使用延迟机制

  1. 下载延迟插件到指定目录

    在 GitHub 仓库中选择合适的版本:https://github.com/rabbitmq/rabbitmq-delayed-message-exchange

    下载适配版本插件到 /usr/lib/rabbitmq/lib/rabbitmq_server-version/plugins 目录: wget uri

  2. 启动插件 rabbitmq-plugins enable rabbitmq-delayed-message-exchange

  3. 在创建交换机是选择 x-delayed-message 类型，在创建交换机的参数中添加参数 x-delayed-type 指定该延迟交换机类型(
    topic direct …)

  4. 在生产的消息头部添加 x-delay 参数设置消息延迟的时间(ms)。
